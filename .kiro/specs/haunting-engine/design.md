# Design: haunting-engine

## Modules

```
engine/src/
  haunting/types.ts      TypeScript view of hauntings/schema.json
  haunting/loader.ts     YAML parse, schema validation (Ajv), semantic rules
  clients/types.ts       Interfaces: ToxiproxyClient, DockerClient, ServiceAdminClient, QueryClient
  clients/*.ts           Real clients: Toxiproxy HTTP, docker CLI, service admin HTTP, Prometheus/Loki HTTP
  faults/drivers.ts      One driver per fault type: capture / apply / restore / probe
  engine/ledger.ts       Ledger of faulted resources, plus memory and file stores
  engine/engine.ts       Engine API: list, apply, escalate, verify, revert, signals, probe
  scoring/index.ts       Deterministic rubric
  mcp/server.ts          MCP tools over stdio
  config.ts              WH_* environment settings, with the sandbox URL guard
```

## The ledger: how reverts stay correct

Every resource a fault touches gets a ledger entry. A resource is a toxic, a service's containers, a config key or a debug toggle. Each entry has:

- `original`: the resource's state, captured before the first fault touched it
- `claims`: a stack with one claim per haunting holding the resource. The top claim decides the current state.

On **apply**, the engine adds a claim, saves the ledger, then writes the top claim to the sandbox.

On **revert**, the engine removes the haunting's claims. For each affected entry:

- If other claims remain, the new top claim is written.
- If none remain, `original` is restored and the entry is deleted.

This keeps overlapping hauntings correct in any order. For example, h1 sets `pool.max_connections=1` and h2 sets it to `2`. Reverting h2 gives back 1, and reverting h1 then gives back the original 20.

A failed restore leaves an entry with no claims. The next revert retries it.

The ledger is written to `engine/.witching/ledger.json` before every sandbox change, so `init()` can undo faults left by a crash.

## Fault drivers

| Type | Resource | Apply | Restore |
|---|---|---|---|
| toxiproxy | toxic `wh_<haunting>_<proxy>_<toxic>_<stream>` | upsert toxic | delete it, or put the original back |
| docker | all containers of a compose service | stop or pause each one | each original container back to its captured state. Containers the player added (scaling) are left alone. |
| config | `service` + `key` via `PUT /__admin/config/:key` | set value | set the original value, or `DELETE` if it was unset |
| debug-endpoint | `service` + `toggle` via `PUT /__debug/:toggle` | `{enabled: true, settings}` | the captured toggle state |

## Sandbox contract (sandbox/ must provide this)

- Compose project label `witching-hour-sandbox` (`WH_COMPOSE_PROJECT`), with services storefront, cart, payments, worker, postgres and queue.
- Toxiproxy on `:8474`, with a `storefront_queue` proxy for the-vanishing.
- App services expose `/__admin/config/:key` and `/__debug/:toggle` (see `clients/service-admin-http.ts`). Default ports are 8081-8084 (`WH_SERVICE_ADMIN_URLS`).
- Metrics: `witching_queue_depth{queue}`, `witching_worker_jobs_processed_total`, `up{job="worker"}`, `http_requests_total{service,code}`, `http_request_duration_seconds_bucket{service,route}`.
- Loki logs labeled `service`.
- Terminal commands `haunt restart|scale|purge-queue ...` must match the strings in each haunting's `fix.actions` and `harmfulActions`.

## Verify and signals

Each check runs one instant query and must return a single series or a scalar. Wrap queries in `sum()`. No series means `emptyValue` if one is set, and fail otherwise. A query error fails the check, and the error is returned as evidence.

## Scoring rubric (v1)

| Part | Points | Rule |
|---|---|---|
| Detection | 30 | Full points up to `detectParSeconds`, then a linear drop to 0 at 4× par |
| Root cause | 10 + 20 | 10 for the right component. Keyword points scale with matched synonym groups up to `minKeywordMatches`, and need the right component. |
| Fix | 40 | Only when `verify()` passed |
| Penalties | −n | Each harmful command, every time. Matching ignores case and extra spaces. |

The total is clamped to 0-100.

## Testing

- Unit tests for every module. Real HTTP and docker clients are tested against stubbed `fetch` and `exec`.
- Property tests run against `test/support/fake-sandbox.ts`, an in-memory sandbox that implements the same client interfaces, with realistic healthcheck delays. Hauntings are generated by `test/support/arbitraries.ts`, which uses small pools so faults often overlap. `generators.property.test.ts` checks that generated hauntings always pass the schema.
- `test/integration/` runs property 1 against the real sandbox when `WH_SANDBOX=1`.
